# ADR-0003 · 检索用二元组 BM25，不引入分词库与向量库

## 状态

已采纳（2026-10-19）

## 背景

知识检索要同时服务两个语料包：

| 包 | 条目 | 片段 | 体积 |
|---|---|---|---|
| `kb-pack.json`（个人知识） | 75 | 549 | 约 1 MB |
| `legal-pack.json`（法律） | 48,620 | — | 40.8 MiB |

运行环境是离线服务器。约束有三条：

1. **完全离线**：不调任何 embedding API（在线调用会让每次代答多一次网络往返与费用）。
2. **零新依赖**：`~/app/.venv` 已装 funasr + torch，加向量库会牵动 torch/numpy 版本。
3. **要能解释**：用户会问「为什么给我这条」，BM25 的命中词可以打印出来，向量相似度不能。

实测过一个现成的法律 MCP 库（B 库），它的 SQLite **FTS5 对中文命中 0 条**——默认分词器不切中文。

## 决策

1. **中文用二元组（bigram）切分**，不引入 jieba。原因：法律条文里大量专名与简称（「民法典」「第五百八十五条」），
   jieba 的自定义词典维护成本高于二元组在长文档上的召回损失。
2. **BM25 打分必须求和，不能取最大值**。
   > 这是修掉的一个真 bug：原实现逐 token 取 `chunk_score` 最大值，导致命中多个词的条文
   > **输给**只命中一个稀有碎片的条文。例如 `违约金太高能少给吗` 首位曾是《刑法修正案（八）》第十五条，
   > 改求和后回到《民法典》第 585 条，且另外 4 组查询排序一字未变。
3. **口语 → 法言法语的扩展词必须进 BM25 参与召回**（权重 0.5），不能只用于重排。
   只重排等于「召回阶段就已经丢了正确条文，后面怎么排都排不回来」。
4. **重排公式**：`BM25/最大值 + 0.45×查询词覆盖率 + 0.25×扩展词覆盖率 + 0.55×最长公共子串/12`，召回 top 60。
5. **跨词二元组碎片进 `STOP_BIGRAMS`**：`能少` / `少给` / `太高` 这类切出来的碎片 IDF 极高，
   会压过真词（`能少` 曾把《刑法修正案（八）》顶到首位）。

## 放弃的方案

| 方案 | 为什么放弃 |
|---|---|
| jieba 分词 | 需要维护法律专名自定义词典；且与「零新依赖」冲突 |
| 向量检索（bge / text2vec） | 需 GPU 常驻显存（与 ASR 抢卡）+ 首次编码 4.8 万条耗时；且不可解释 |
| 在线 embedding API | 每次代答多一次网络往返与费用；离线不可用 |
| 用 B 库自带的 SQLite FTS5 | 实测中文命中 0（默认分词器不切中文） |
| 起 MCP 子进程接法律查询 | 每次查询一次进程通信开销；且三铁律（过滤在检索之前）无法在外部库内保证 |

## 重评条件

- 若检索首位命中率长期低于 **70%**（当前 10/17 ≈ 59%，top3 14/17 ≈ 82%），说明规则表已到天花板，应上向量召回做 rerank；
- 若显存预算允许且 ASR 改为按需加载，可评估本地 embedding（仍需保留 BM25 做混合召回）；
- 若 `legal-pack.json` 超过 100 MB（内存常驻已 433 MB），应改为分片加载或换倒排落盘。
