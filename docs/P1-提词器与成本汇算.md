# P1：提词器 + 成本汇算

2026-10-19 落地。两项都是「不给用户加负担」的设计：提词器只在你需要时出现，
成本只在角上显示两个数字，明细去命令行看。

---

## 一、提词器

### 它和解说式的「AI 助手」有什么不同

| | 代答（`sayDraft`） | 提词（本功能） |
| --- | --- | --- |
| 产出 | 一整句能直接念的台词 | 1~2 条极短提示 |
| 谁来说 | 分身用你的音色说 | **你自己说** |
| 是否合成 | 是（走 TTS，成本大头） | 否（零 TTS 成本） |
| 触发 | 喊名字 / 连着说话 / 手动点 | 对方每说完一句，防抖 1.2 秒后 |

一句话：代答是「替你说话」，提词是「提示你说什么」。后者更便宜，也更自然——
真人对话里你不需要别人替你说，只需要有人递个话头。

### 怎么用

1. 开始录音（和平时一样）。
2. 「分身混音」里确认 **提词器** 已勾选（默认开）。
3. 对方说完一句，面板顶部出现 `提词` 条，每条前面有个小标签：
   - `接` — 可以直接接的话
   - `问` — 该追问什么
   - `核` — 涉及数字/承诺，先别答应，先确认
4. 两个按钮：
   - **填台词框**：把提示塞进「让它说」的输入框，改完再点「让它说」。
     提示是「要点」不是「台词」，直接念会很生硬，所以这里只填不发。
   - **再想一次**：绕过防抖立刻重问一次。
5. 快捷键：`P` 收起/展开提词条（收起状态下按 `P` 会立刻要一条新的），`Esc` 收起。

### 三条防止「帮倒忙」的规则

1. **防抖 1.2 秒**：对方还在说的时候不发请求。半句就发一次，一句话能烧三次 token，
   而且拿到的上下文是残缺的，提示质量更差。
2. **双缓冲**：新结果没回来之前，屏幕上保留上一条。否则每次定稿都闪一下空白，
   人正读到一半被清空，比不给提示还烦。
3. **手动滚动后 3 秒不抢滚动条**：提词区、转写区都是。他在往回看，别把他拽回底部。
   滚回底部立即恢复跟随。

### 英文注音：查字典，不调模型

中文里夹 `api` / `budget` 这类词，念出来容易卡。注音是**本地字典**做的
（`prompter.PHONETIC`，约 30 个高频词），不花 token、不联网、结果稳定。

- 全大写、≤5 个字母的缩写（`ASAP` / `CEO` / `KPI`）**跳过**——念字母本身就够清楚，
  再注音反而绕。
- 字典里没有的词不注。乱注比不注更难念。
- 同一句里同一个词只注第一次。

默认关闭，在「分身混音」里勾 **英文词注音** 才生效。注音版本后端随提词一起下发，
切换开关不会再发请求。

### 实测

| 场景 | prompt | completion | 耗时 |
| --- | --- | --- | --- |
| 提词（3 句上下文） | 313 | 16 | 1.6s |
| 代答（同上下文） | 613 | 25 | ~2.5s |

提词的输出只有代答的 2/3 长度、约 1/2 的 prompt（不提「一两三句怎么说」的约束），
又不触发 TTS——按 2026-10-19 的成本实测，**单次提词的成本约为一次出声代答的 1/10**。

实际输出样例（对方在压价）：

```
[接] 先别降，讲清贵在哪
[核] 差价四千，先确认对方口径
```

## 二、成本汇算

### 为什么要分两个口径

一个数字说明不了问题。必须分开：

- **折算价（fair_yuan）**：这些活儿如果交给云端同款模型，要花多少钱。
- **实付（cost_yuan）**：你真掏出去的钱。本地模型恒为 0，只单列电费。

两者之差就是「本地部署省下的钱」。混在一起算，就永远看不出本地部署值不值。

### 记在哪

| 文件 | 内容 |
| --- | --- |
| `~/data/pricing.yaml` | **价格表，唯一真源**。改完自动生效（按 mtime 重载），不用重启 |
| `~/data/usage.jsonl` | 账本，一行一次调用 |
| 归档的 `report.md` 末尾 | 「本场累计成本」块，随纪要一起進 Gitee |

### 价格口径（2026-10-19）

| 项目 | 单价 | 对标 |
| --- | --- | --- |
| LLM（deepseek-flash） | 高峰 命中输入 0.1 / 未命中 3 / 输出 9（元/百万 token）<br>谷时 0.05 / 1.5 / 4.5 | 厂商现价 |
| ASR（paraformer-zh） | 0.288 元/小时 | 阿里云百炼 Paraformer 录音文件识别 |
| TTS（cosyvoice2） | 2.00 元/万字符 | 阿里云 CosyVoice 大模型 |
| 电费 | 按整机 150~300W、¥0.6/度估算，约 ¥0.1~0.2/小时 | 自填实测值替换 |

两个必须写死的细节：

1. **CosyVoice 计费口径是「1 个汉字 = 2 个字符」**。一个 27 字的中文句子算 50 个字符。
   写错一倍，整个成本结论就偏了。
2. **谷时按北京时间 00:30–08:30 + 周末全天**。`pricing.yaml` 里可改。
   拿不到缓存命中信息时按「全部未命中」算——宁可高估，不要低估。

### 埋点在哪

| 位置 | kind | ref |
| --- | --- | --- |
| `server.py /api/tts` | tts | 会话 id（实时）|
| `server.py /api/assistant/reply` | llm / assistant | 会话 id |
| `server.py /api/prompter/suggest` | llm / prompter | 会话 id |
| `server.py` ws 结束时 `_log_live_asr` | asr / live | 会话 id |
| `transcribe.py` 转写完成 | asr / archive | 工作目录名 |
| `summarize.py` 纪要完成 | llm / summary | 工作目录名 |

**ref 的迁移**：转写/纪要在归档之前发生，那时 `meeting_id` 还不存在，只能用工作目录名
占位；归档时 `costs.relabel()` 一次性改写成 `meeting_id`，实时会话的账在
`_finalize` 里同样并过去。所以查一场的成本，要用 `meeting_id`。

> 踩过的坑：`_log_live_asr` 一开始放在 ws 的 `finally` 里，比 `_finalize` 的 relabel 更晚，
> 结果实时那笔账永远挂在 session id 上、并不到场次名下。现在改为在 `_finalize` 开头就记，
> 并加 `_cost_logged` 幂等标记。

### 在哪看

**网页**：右上角徽标，录音时每 12 秒刷一次。

```
¥0.0088 · 省 0.0051
```

悬停看明细：折算 / 实付 / 本地省下。归档后自动切到 `meeting_id`，数字会并入实时那部分。

**命令行**：

```bash
cd ~/app
.venv/bin/python cost_report.py                  # 最近 7 天
.venv/bin/python cost_report.py --days 30
.venv/bin/python cost_report.py --ref M20260101-100000-bbbb
.venv/bin/python cost_report.py --top 10         # 最贵的 10 场
.venv/bin/python cost_report.py --markdown       # 可粘进文档
.venv/bin/python cost_report.py --json
```

**网页接口**：`GET /api/cost?ref=<meeting_id|session>`、`GET /api/cost?since=2026-10`。
按 `owner` 过滤——同一台机器上另一个口令看不到别人的账单。

### 实测（32 秒双人对话，一次完整流程）

| 项目 | 次数 | 用量 | 折算 | 实付 |
| --- | --- | --- | --- | --- |
| 语音转写 | 2（实时 + 归档） | 1.1 分钟音频 | ¥0.0051 | ¥0 |
| 大模型 | 1（纪要） | 549 入 / 271 出 | ¥0.0037 | ¥0.0037 |
| 电费 | — | — | — | ¥0.0024 |
| **合计** | | | **¥0.0088** | **¥0.0061** |

本地省下 ¥0.0051（58%）。

### 结论：省钱的优先级

1. **缩短播报长度**。TTS 占单场成本约 87%（按 100 秒会议实测：TTS ¥0.2048、
   LLM ¥0.0222、ASR ¥0.0078）。一个汉字两个计费字符，少说一句比换便宜模型有效得多。
2. **多提词、少出声**。「只听不说」+ 提词，比自动代答便宜一个量级——
   不触发 TTS，提示本身也只花十几个输出 token。
3. **别指望换便宜 LLM**。LLM 只占约 10%，再省也就省个零头。

成本自检里有几条是「反向对照」：故意让规则失效，断言必须失败。比如

## 四、已知限制

1. **实时流式 ASR 的成本按音频时长折算**，不是按真实 GPU 时间。流式识别本来就跟音频
   实时跑，这个近似够用；离线转写用的是真实计算耗时。
2. **电费按整机 150~300W 估算**，不同负载会有出入，占比很小（约 0.5%~25%，看场景）。
3. **重跑会累加**。同一场用 `refresh_archive.py` 重跑一次，这一场就真的又花了一笔，
   成本块标题写的是「本场**累计**成本」，账不抹。想看单次，用 `--top` 按时间对。
4. **缓存命中要服务端返回才准**。DeepSeek 会返回 `prompt_cache_hit_tokens`；
   不返回的服务端按全未命中算（高估）。
5. **提词依赖 LLM 在线**。断网/超时就静默不显示，不弹错误——它是辅助功能，
   不该打断对话。
