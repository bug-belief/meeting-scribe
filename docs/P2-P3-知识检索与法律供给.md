# P2-1 知识检索层 + P3 法律知识供给

> 2026-10-19 上线。目标是让「语音分身」知道自己是谁，而不只是会接话。

---

## 一、为什么先做检索层

P1 结束时，助理能接话、能提词，但它**只看得见当场那几句对话**：

- 对方问「你之前不是做过那个项目吗」，它只能含糊过去；
- 对方问「定金不退合法吗」，它只能凭训练数据泛泛而谈。

这两件事都不是模型能力问题，是**没给它资料**。所以 P2 的第一件事不是「教它说话」，
而是**让它能查到东西**。

## 二、检索层怎么做的

### 2.1 为什么不用 RAG / 向量库

| | BM25（本方案） | 向量检索 |
|---|---|---|
| 语料规模 | 75 条 / 1.2 MB、548 段 | 同左，但为它准备的 |
| 依赖 | 纯标准库 | 嵌入模型 + 向量库，约 1-2 GB |
| 可解释 | 能说「命中第几段、哪个词」 | 只能给相似度 |
| 更新 | 重跑 60 ms | 要重新嵌入 |
| 适用临界点 | 千条以内 | 数千条以上、语义模糊查询 |

两位数条目用向量库属于过度设计。**真到几千条再换**，接口不变。

### 2.2 中文怎么切词

不引 jieba（多一个依赖、多一处环境不一致），用**字符二元组**：

```
「拆单合并」→ 拆单 / 单合 / 合并
```

配合一份约 30 个词的虚词二元组黑名单（`的的`/`我们`/`可以`…），
两个字的查询也能命中。英文按词切并转小写。

### 2.3 三件事决定检索能不能用

| 机制 | 做法 | 为什么 |
|---|---|---|
| **切块** | 按 markdown 标题切，16~700 字 | 整篇 8 KB 塞进 prompt 会冲淡重点、烧 token；切块才能「命中哪一段」 |
| **标题/标签加成** | BM25 分 ×(1+命中词数×0.35) | 纯 BM25 只看正文，会把「标题就是这个意思」的条目排低 |
| **片段清洗** | 去 wiki 链接、HTML 注释、列表号、加粗、溯源注脚 | 不清洗模型会学这些符号，甚至在回答里复述出来 |

## 三、隐私：过滤在检索之前

这是整套设计的地基，**不是在结果上打码**：

| 层 | 动作 | 结果 |
|---|---|---|
| 构建期 | `visibility: secret` 的条目**不进索引包** | 线上文件里根本不存在这些内容 |
| 构建期 | `background.md`（底稿）**不进包** | 「给自己看的」和「能对别人说的」物理分开 |
| 查询期 | 只放行 `public`/`internal` | 再挡一道，双保险 |

`background` 档（自述、草稿这类底稿）**默认不注入**——适合自己看，不适合让助理在电话里张口就来。
确实要用时设 `KB_ALLOW_BACKGROUND=1`。

> 自检里有一条反向对照：强制 `--include-secret` 后能搜到那条 secret 样本，
> 加了 visibility 闸门后搜不到。证明闸门不是摆设。

## 四、接入方式

```
对方说完一句
   ↓
kb_bridge.build_query()  取最近 3 句 + 待回应内容
   ↓
kb_search.search()       个人 KB 与法律语料各查一次，合并排序
   ↓
kb_bridge.context_for()  按 700 字预算拼成「【背景知识】…」块
   ↓
assistant.draft_reply() / prompter.suggest()  拼进 user 消息
```

四个设计约束：

1. **检索失败绝不能让代答失败**——全部异常吃掉，返回空串；
2. **按 mtime 懒加载**——改了索引包不用重启 `meeting-web`；
3. **只取最近 3 句**做查询词——再往前的话题多半翻篇，带进来反而稀释关键词；
4. **注入块里明确写「对不上就当没看见」**——防止模型拿沾边资料硬编。

可调环境变量：`KB_PACK` / `KB_LEGAL_PACK` / `KB_ENABLED` / `KB_TOP_K` / `KB_BUDGET` / `KB_ALLOW_BACKGROUND`。

## 五、P3：法律知识

### 5.1 三层供给（设计见产品化文档第 12 节）

| 层 | 内容 | 状态 |
|---|---|---|
| **L1 本地** | `knowledge/legal/` 里放法条原文，不联网可查 | ✅ 本次落地 |
| L2 Connector | 接专业法律数据库做实时检索 | 待用户选（已弹过推荐卡） |
| L3 大模型 | 只做解释，**不引条号** | 约束写进语料说明 |

L3 那条是防幻觉的关键：模型编一条不存在的法条，比说「我不确定」危害大得多。

### 5.2 法条是怎么来的（这一节最重要）

**不能靠模型转述**。它会把「可以请求适当减少」写成「应当减少」——一字之差，性质变了。

尝试过、失败的路径：

| 路径 | 结果 |
|---|---|
| `flk.npc.gov.cn/api/` | 已改前端渲染，返回 SPA 外壳，不是 JSON |
| 人大网民法典全文页（两个已知 URL） | 302 到首页，ID 已失效 |

最后走的路：**抓法院/检察院站点，做多源一致性校验**。

```
① 中国法院网 / 若干地方法院官网（北京、江苏、山西、河南）
   最高法人民法庭信息网 ……（域名白名单写死在脚本里）
② 最高人民检察院官网《民法典》第三编 合同 **整编全文**  ← 基准
③ 逐条比对：短摘引必须是全文的连续子串，或 4-gram 相似度 ≥0.9
④ 官方全文直接收（tier=official）；零散摘引必须 ≥2 源一致（tier=cross）
   单源摘引一律丢弃 —— 抄错了没人能发现
```

结果：**526 条**（合同编全部条文），每条一个 md 文件，带来源与抓取日期。

### 5.3 踩到的三个坑

1. **正文里的条文引用会被当成新条号**
   「依据本法第五百一十条」——若按任意位置匹配条号，当前条文会被拦腰截断。
   修法：只认**行首**条号，且块级标签必须先换成换行（否则整页压成一行，行首永远不成立）。

2. **最后一条会连着页面尾巴**
   抓「最后一条」时正文一路连到「责任编辑」「友情链接」「版权所有」。
   修法：一张尾部标记表，从首次出现处截断。

3. **「只有 2 个来源」不等于「2 源一致」**
   一个站点只引第一款、另一个引全文，逐字比对必然不等。
   修法：短的必须是长的连续子串才算一致——**摘引不是差异，抄错才是**。

### 5.4 诚实标注

每条都写：

```
> 官方全文 最高检·民法典第三编合同（全文）、两家地方法院官网摘引
```

文件头统一声明：**未与国家法律法规数据库逐字核对**（该库取不到）。
用途是「谈判/沟通时把话说准」，不构成法律意见。

## 六、怎么维护

```bash
# 个人 KB：改完条目后重建
python tools/kb_search.py build --out ~/data/kb/kb-pack.json      # 本机跑，然后 scp

# 法律语料：加来源 / 重抓 / 重建索引

python deploy/fetch_legal.py
python kb_search.py build --flat knowledge/legal --out ~/data/kb/legal-pack.json
```

⚠️ 重抓法条后**必须重建索引包**，否则检索仍是旧条文。

## 十、P2-2 字段级脱敏 + P2-3 场景包（2026-10-19 上线）

### 10.1 脱敏：过滤仍然发生在检索之前

`visibility` 管条目，管不了正文里随手写的手机号。而索引包一旦被检索注入，
那串数字就顺着代答念出去了。所以 `tools/redact.py` 在**构建期**替换，
线上文件里根本没有明文。

**纯正则必然误伤**。实测 KB 68 条：`\d{16,19}` 命中 22 处全是小程序 appId，
`@` 3 处全是文件名（`README@2026.md`）。所以每条规则都有第二条腿：

| 类型 | 反误伤条件 |
|---|---|
| 手机号 | 两侧非字母数字 + 11 位 + 第二位 3-9 + 不是 8 个以上同数字 |
| 身份证 | 出生日期合法才认；**校验位对得上 → high，对不上 → medium「待核」** |
| 银行卡 | Luhn + BIN 首位 3/4/5/6；**或**前方 16 字内有「卡号/转账/尾号」 |
| 邮箱 | TLD 不能是文件后缀（`.md/.py/.json/...`） |
| 令牌 | `sk-`/`ghp_`/`AKIA`/私钥块；`xxx`、全同字符、`<your-token>` 视为占位符 |

三处设计取舍值得记下来：

1. **校验位不对的身份证仍然要挡**（降为 medium 并标「待核」）。手抄错一位的
   身份证照样是身份证，直接放行等于留个洞。
2. **银行卡改为「Luhn + BIN」或「有上下文词」二选一**。只认 Luhn 时，18 位
   订单号有 1/10 概率撞上校验位；只认上下文词又会漏掉裸写的卡号。
3. **豁免区必须先算**：围栏代码块、行内代码、URL、文件路径整段不动。
   不先切出豁免区，README 里那些 `13812345678` 示例代码就会被改掉。

模式：`warn`（默认先看误伤率）/ `mask`（构建期替换）。
构建入口 `kb_search.py build --redact=mask|warn|off`。

### 10.2 场景包：领域 + 听众两道闸门

条目新增两个字段（都可以不填，不填就自动推断）：

- `scopes`：`career/tech/legal/finance/personal/general`，最多两个
- `audiences`：`self/friend/client/recruiter/public`

推断用 title + tags + keywords，**故意不算 summary**：算上 summary 时
「系统」「开发」几乎每条都中，tech 会覆盖 66/75 条，过滤等于没做。

`audience` 的收窄规则也很克制——**只有 `scopes == ["personal"]`（唯一领域
就是私人生活）** 才挡掉 client/recruiter。理由：一条技术类个人作品会推断出
`personal + tech` 两个领域，那是作品不是家务事，不该因为沾了生活关键词就不许在对外场合讲。

场景配置 `~/data/kb/scenarios.yaml`（模板 `deploy/scenarios.yaml`），
按 mtime 热加载。五档：`default` / `meeting` / `interview` / `negotiation` / `call`。

### 10.3 实测

| 查询 | default | interview | negotiation |
|---|---|---|---|
| `定金不退能退吗` | 民法典 586 / 587 | **0 条**（法律不在面试域） | 民法典 586 / 587 |

示例库：`recruiter` 听不到 2 条（都是 `background` 档底稿）；
`client` 同样 2 条。其余 73 条按领域筛。

### 10.4 测试

- `tests/test_redact.py` 42 项，其中 13 项是**反向对照**（appId / 文件名 /
  行内代码 / URL / 路径 / 订单号 / 占位符，要求一处都不动）；
- `tests/test_scenario.py` 26 项，重点是「该挡的挡掉了」，以及
  「旧包缺字段不被误杀」。

> ⚠️ 测试里 `KB_LEGAL_PACK` 要指向**不存在的路径**而不是 unset：
> 服务器上 `~/data/kb/legal-pack.json` 是真的，unset 会让法条挤进结果，
> 测的就不是自己造的那几条了。
