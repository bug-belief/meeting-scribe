# 声纹库与语音分身（阶段 2B）

> 首次整理：原根目录 `README.md` 第 10 节全段（2026-10-20 拆分）。原文逐字保留，未改写。

## 10. 声纹库（阶段 2B）

把每次会议都重新编号的 `Speaker 1/2`，变成跨会议稳定的人名。

### 10.1 原理

声纹分离出来的每个簇有一个 192 维质心（cam++）。拿它和 `data/speakers.json` 里已登记的人比对余弦相似度，
按三档处理：

| 信道 | 自动命名 | 给候选 | 说明 |
|---|---|---|---|
| close（耳机/近场） | ≥ 0.70 | 0.56–0.70 | 干净信道，可以全自动 |
| far（免提/会议室） | ≥ 0.66 | 0.54–0.66 | 混响大，相似度整体偏低 |
| phone（电话窄带） | ≥ 0.78 | 0.56–0.78 | 两人声纹只差 0.05 量级，宁可不认也不认错 |
| unknown（自动判不出） | ≥ 0.68 | 0.56–0.68 | 按原始采样率/码率自动归类 |

信道由原始音频的采样率和码率自动判断（转 16k 之前，否则线索就没了）。

> **双路分轨录音不走这里**：它按左右声道直接判人，声纹库只对麦克风/上传音频生效。
> 两种模式可以共存——同一个人既想按声道分，又想以后被声纹认出来，就分别录两次入库。

### 10.2 日常用法

```bash
# 1) 跑完一次，看识别成什么样（会列候选和相似度）
python tools/speaker_cli.py show --dir processed/2026-01-01_电话录音

# 2) 确认某个簇是谁：入库 + 顺手改名
python tools/speaker_cli.py label --dir processed/2026-01-01_电话录音 --cluster 0 --name 张三

# 3) 用一段干净的单人录音直接入库（推荐：安静房间、5–10 秒、3 种语气）
python tools/speaker_cli.py enroll --name 张三 --audio ~/samples/me.m4a --channel close

# 4) 这段录音像谁
python tools/speaker_cli.py who --audio ~/samples/test.m4a

# 5) 维护
python tools/speaker_cli.py list
python tools/speaker_cli.py rename --old 张三 --new 张老师
python tools/speaker_cli.py forget --name 张三
```

确认过一次之后，下次同一个人的录音会直接显示名字，不用再点。

### 10.3 几个必须知道的细节

- **每人多模板**：手机、耳机、会议麦是三种声纹，默认最多存 5 条，按信道区分。
- **还要按场景分**：同一个人闲聊、开会念稿、说方言，声纹差别比「换设备」还大，见 10.3.1。
- **只对干净片段入库**：时长不足 1.2 秒、或两人同时说话的混合声纹不入库（会污染）。
- **只让真正的语音进质心**：取窗时会做 VAD + 相对能量门限（≥ 最强窗的 25%），再按能量加权平均。
  早期版本直接取前 60 秒整段平均，把静音和对方声音一起搅进去，造出过一条「和谁都不像」的脏模板。
- **阈值有实测依据**，见 10.3.2；不要凭感觉调。
- **库是敏感数据**：`speakers.json` 权限 600，只存本地，不要提交到 git、不要上传。

### 10.3.1 场景（语域）：同一个人在不同场合的声音不一样

你的直觉是对的，而且实测差距很大：

| 关系 | 相似度 | 结论 |
|---|---|---|
| 同一段录音自比（检验提取是否稳定） | **0.96** | 提取没问题 |
| 同语域跨录音（都是自然对话） | **≈0.56** | 可以直接自动命名 |
| **跨语域**（一次念稿 vs 一次闲聊） | **≈0.30** | 只给候选，要人确认一次 |
| 不同人 | **0.11** | 未知 |

所以声纹库从「人 × 信道」升成「人 × 场景 × 信道」。同一人可以有多套场景：

```
张三
├─ 默认   （日常对话）
├─ 开会   （念稿、正式表达）
└─ 方言   （家乡话）
```

**场景只能人工标，系统猜不出来**——无标签聚类只能告诉你「这几簇不像同一个人」，
它没有语义，不可能自己知道「这是方言」。所以认领时顺手在下拉里选一下：

- 网页：结果面板 → 说话人那一行 → 「这是谁？」旁边的场景下拉 → 选「开会 / 方言 / 日常 / 电话」
- 命令行：`python tools/speaker_cli.py enroll --name 张三 --audio 开会录音.wav --profile 开会`

标过一次之后，同一场景的录音就能自动认出来（实测：标完「开会」后，那段念稿录音的相似度从 0.30 升到 **1.00 / auto**，而对话录音仍走「默认」模板 0.96）。

**合成也跟着分场景**。音色目录改成两层，一个场景一个音色：

```
~/tts/voices/张三/默认/prompt.wav       → voice id = 张三
~/tts/voices/张三/开会/prompt.wav       → voice id = 张三@开会
~/tts/voices/张三/方言/prompt.wav       → voice id = 张三@方言
```

```bash
python voice_register.py --name 张三 --profile 开会 --audio 开会录音.wav --start 10 --end 25
```

⚠️ **必须分目录，不能混**。CosyVoice2 的 `add_zero_shot_spk(id, prompt)` 是「一个 id 绑一个 prompt 音频」，
同名重复注册是**覆盖**不是平均。把三段声音塞进同一个 `zhangsan`，最后只有最后一次生效。

⚠️ **克隆会连口音一起克隆**。给方言参考音 + 普通话文本，出来的是「带方言腔的普通话」，
不是用方言念字——除非文本本身就是方言写法。

### 10.3.2 阈值是怎么定出来的（2026-10-19 实测）

旧阈值是 `auto 0.70 / cand 0.56`，正好压在同人分数（0.56）上，结果是**每次新录音都掉成 unknown、
逼你重新认领**。用四组对照重标后：

| 信道 | auto（自动命名） | cand（给候选） |
|---|---|---|
| close（近场） | 0.50 | 0.28 |
| far（远场） | 0.48 | 0.26 |
| phone（窄带） | 0.56 | 0.32 |
| unknown | 0.50 | 0.28 |

外加一条硬规则：**第一名要比第二名高 0.10 才给自动命名**（`AUTO_MARGIN`）。
分数够了但两人咬得很紧时，宁可降级成候选让人点一下。

复核方式（不用麦克风）：

```bash
python tests/emb_diag3.py          # 打印同人/异人的实测分布
python tools/speaker_cli.py who --audio 某段录音.wav
```

### 10.3.3 双声道：对方那一路不自动命名

双声道下右声道就是对方，但外放、串音、混响会让对方的声音「长得像你」——
实测对方簇与说话人本人模板的相似度有 **0.564**，已经过了 auto 线 0.50。所以：

> **属于对方声道（right）的簇，即使分数过线也只给候选，不自动命名。**

左声道（你自己）不受影响，正常自动认。对方要入库就手动认领一次。

### 10.4 多人共用：每人一个租户

一个人一套目录，互相看不见。

```
data/tenants/<owner>/
├── audios_inbox/     # 手机同步进来的原始文件
├── processed/        # 归档：音频 + 转写 + 纪要 + 回放
├── work/             # 中间文件、state.json
└── speakers.json     # 这个人的声纹库（别人看不到）
```

```dotenv
WEB_TOKEN=我的口令
DEFAULT_OWNER=me
# owner:token，逗号分隔。owner 名只用于区分目录，随便起
TENANT_TOKENS=me:我的口令,alice:另一个人的口令,bob:第三个人的口令
```

- 口令由 `?k=<口令>` 或 cookie `wb_k` 带上来，鉴权中间件解析成 `request.state.owner`，
  后面每个端点用 `for_owner()` 派生一份 `Settings`，`inbox / processed / work / speakers.json` 整体换掉，
  **管线代码一行没改**。
- `GET /api/me` 看自己是谁、根目录在哪、以及当前跑的是哪次提交（`build`）；
  `GET /api/health` 免鉴权，只回 `ok / version / model_loaded / sessions`——
  不报租户数、设备数与任何路径（那等于把内部结构递给扫描器）。
- 加人：`.env` 加一项 + 重启服务，目录自动建。没有对应口令的请求一律 401。
- 迁移旧数据：`python deploy/migrate_tenants.py --dry-run` 先看清单，再去掉 `--dry-run` 真搬。
  幂等、只 `move` 不删除，目标已存在就跳过，可重复执行。
- 回滚：把 `data/tenants/me/` 下的 `processed / work / audios_inbox / speakers.json` 搬回 `data/`，
  旧版代码不认 `tenants` 目录，搬回去就回到单租户布局。

几个坑：

- **归档目录名会跨租户重名**（都有 `2026-01-01_会议_1000`），所以回放缓存放 `work/_playback/<owner>/`，不会串音。
- **`watcher.py` 只跑默认租户**：手机 Syncthing 自动同步那条链路没有多租户。多人共用一台机时，
  各自用不同同步目录（或干脆只用网页录音），否则文件会全落进 `me`。
- **声纹库各自独立**，同一个人在两个租户里要各登记一次。这是隐私上正确的做法，不做共享。

### 10.5 网页里认领没识别出来的说话人

以前只能 `python tools/speaker_cli.py label`，现在页面上直接点。

结果面板里「说话人」区会列出每个未识别的簇：编号、时长、句数、相似度；
点「试听」听这一簇里最长的一句（自动剪 3–6 秒），听出来是谁就填名字 → 「认领」。
认领完稿子当场刷新，下次同一段语音就能自动认出。

后端三步：

| 路径 | 作用 |
|---|---|
| `GET /api/archive/speakers?dir=` | 拿分配结果（embedding 已剥掉，不外传） |
| `GET /api/archive/cluster_audio?dir=&cluster=` | 剪一段 mp3 试听，缓存在 `work/_cluster/` |
| `POST /api/archive/claim` | `claim_cluster()`：质心入库 + 改 `speakers.json` + 改写 `transcript.md` |

几个坑：

- **入库用簇质心，不是挑一句**。挑单句遇到噪声/抢话就把声纹带偏了；质心是多窗口平均，稳得多。
- **双声道录音的标签是「我/对方」，不是 `Speaker N`**。改写时从 `transcript.json` 的 `speaker_names`
  取旧名当别名，否则找不到要替换的标签。
- **只替换标签位**（`] X**：` 和 `**X**：`），正文里恰好出现同名的字不会误伤；抬头 `> 说话人：` 那行一起刷新。
- 认领后同一质心重新比对是 `auto 1.0`，其他人 0.005 / 0.052 —— 不会顺带把别人认成你。

### 10.6 助理的声音单独标

语音助理用的是你的克隆音色，声纹上**和你本人几乎重合**，靠声纹一定分不开。
所以按**播报时间线**判：页面开播时发 `tts_begin`，说完或被打断发 `tts_end`。

```jsonc
{"type":"tts_begin","id":"u3","text":"这句要念的话","voice":"zhangsan","at":12.4}
{"type":"tts_end",  "id":"u3","at":16.9,"spoken_chars":18,"state":"done"}  // done | partial | cancelled
```

服务端 `apply_assistant_timeline()` 的判定：

- 与播报窗口重叠 ≥ 15% 段长的句子 → 整句判助理
- 重叠 10%–15% → 仍是助理，但只算重叠进去的那部分
- **没有任何句子覆盖到这条播报的 30%** → 说明合成音根本没进录音（虚拟声卡不回环时很常见），
  按 `spoken_chars` 截断文本后**补一段**进去

助理用伪 id `ASSISTANT_SPEAKER = 9001`，落在双声道编号之外（左 0–999 / 右 1000–1999），不会和真人撞车；
`speaker_count` 也不算它，所以「说话人 3 位」里不会有它。

实测（20 秒单声道，0.6→2.4s 插一条播报）：

```
meta.assistant_events = [{"id":"demo1","start":0.6,"end":2.4,"spoken_chars":26,"state":"done"}]
transcript.md  **[00:00:01] 助理（我的声音）**：这是助理说的测试台词…
转写提示      助理时间线：1 条播报记录，改写 0 句、补充 1 句（合成音未进录音，文本取自播报日志）
```

- `state=cancelled` 的句子**既不进稿子也不进回放**——回放放的就是录音本身，没播出去自然没有。
- 已经播出去的部分留在录音里，所以混音听得见、稿子也看得见，两边天然一致。

**两条必须守住的实现约束（都是实测踩过的）：**

1. **任何从本机放出去的合成音都必须上报事件。** 之前「试听」按钮直接 `ttsAudio.play()`，
   绕过了 `tts_begin/tts_end`，那句合成音就被当成陌生人——而且它走 CABLE 被系统声卡抓进右声道，
   最后标成了「对方」。现在 `announceBegin()/announceEnd()` 是唯一入口，试听也走同一条路。
2. **时间线标注必须在 `merge_turns()` 之前。** merge 会按说话人把相邻句并成一段，
   如果先合并，助理那几句会和前后人声并进同一段，整段被判成助理（连带把真人的话也吃掉）。
   顺序反了不会报错，只会安静地错——所以 `tests/test_assistant.py` 专门加了三条顺序断言。

**仍然存在的边界**：这套机制完全依赖前端把事件报全。网络抖动、页面崩溃、刷新都会丢事件，
丢了就只能回落到声道/声纹判断，可能把那句标成「对方」。要彻底消除，
需要在服务端（CABLE 出口处）另做一路录音旁路，目前没做。

### 10.7 台词队列：先看稿、逐句跟进、打断作废

页面右侧「说话」面板：选音色 → 输入整段话 → 点「说」。
队列按句号 / 问号 / 感叹号 / 换行切句，**逐句合成、逐句播放**，同时预取下一句。
所以第一句一开口，后面的稿子已经在屏幕上排好了。

| 状态 | 含义 | 稿子 | 回放 |
|---|---|---|---|
| 待说 | 还没轮到 | 无 | 无 |
| 正在说 | 播放中，句内进度按 `currentTime / duration` 估算，逐字高亮 | 有 | 有 |
| 已说完 | 播完了，对方已经听到 | 有（全文） | 有 |
| 已作废 | 被自己打断或点了停止 | 无 | 无 |

- 句内进度是**比例估算**（已播秒数 / 本句时长 × 本句字数），不追字级时间戳——够用且便宜。
- 打断时发两条 `tts_end`：当前这句 `state=partial` 且 `spoken_chars` 按比例算，后面没播的全部 `cancelled`。
- **不做「续说」**：打断往往意味着对方刚插了新内容，硬续会把旧答案塞回去。
  想接着说就在下一条指令里写「继续说」，模型会带着新上下文重新组织。
- 点「停」或关掉录音都会先走一次 `sayInterrupt()`，保证队列状态和录音里的实际内容一致。

### 10.8 「接一句」：让分身自己组织回答

10.7 解决的是「怎么把它的话说出来」，这一节解决「说什么」。

```
点「接一句」  ──┐
                ├─→ POST /api/assistant/reply {session}
喊「语音助理」 ──┘            ↓
                        取 LiveSession.lines 最近 14 句
                        + 自己刚才说过的那几句（sess.events）
                        + 当前日期时间
                              ↓
                     DeepSeek flash 生成 1–3 句 / ≤80 字
                              ↓
                     填进台词框 → 自动开播（走 10.7 的队列）
```

几处刻意的设计：

- **上下文用服务端实时行，不用前端传**。会话 id 由 WS 的 `ready` 给出，服务端按 `owner` 校验，
  跨租户拿不到别人的上下文（403）。页面刷新过、会话已收尾，才退回用前端带上来的文本。
- **连续对话（2026-10-19 改）**：喊一声「语音助理」后进入 **90 秒对话窗口**，
  窗口内接着说话（不管是谁说的）都会自动接，不用每句都重新喊。
  两条防自激：正在播报时不触发；播报结束后 1.5 秒内的声音当作「自己录回来的」不触发。
- **能答就答（2026-10-19 改）**：旧提示词写死「只用出现过的信息」，问天气只会回
  「这个我确认一下」——听起来像坏掉了。现在改成：常识、客套、能从上下文推的直接答；
  只有「具体数字/金额/时间/承诺且没出现过」「需要查实时信息」「指代不明」三种情况才兜底。
  绝不编造事实这条没松。
- **知道自己说过什么**：`sess.events` 里 `done/partial` 的台词会作为「你刚才说过」喂给模型，
  否则每轮都当第一次见面，会重复自我介绍。
- **实测量级**：3 句上下文 → 1.2 秒出稿（`deepseek-flash`，prompt 265 / completion 14 tokens）。
- **醒来就知道今天几号**：每次代答都注入当前日期时间，否则它答不了「明天」「后天」这类相对时间。
- **实时信息按需现查**：问到天气会去 `wttr.in` 取未来三天（温度区间、天气、降雨概率），
  10 分钟缓存。只有命中「天气/气温/下雨/冷不冷/穿什么/带伞」才发请求，其余零成本。
  提示词里写死「温度区间和降雨概率必须逐字照抄，不许四舍五入、不许说『六成多』」——
  实测不加这句，模型会把 `9~15℃ / 28%` 改写成 `11 到 17 度 / 六成多`。
  查不到就什么都不加，模型按「手上没有」处理，不编。
- **唤醒开关默认开**（`sayWake` 带 `checked`）：这是「语音助理」的默认形态。
  不想让它自动接话就取消勾选，退化为纯手动「接一句」。

另外加了「试听」按钮：不写台词也能合成一句「喂，能听到吗？我是你的声音分身在说话。」，
走的是**和正常播报完全相同**的通路（CABLE + 耳机监听），用来单独验证声音有没有出去。

### 10.9 双路分轨：右声道没声音会明确告警

以前这种情况只会安静地出一份「只有我一个人说话」的稿子，看不出哪里错了。
现在页面盯着右声道能量：录满 8 秒、右声道最大 RMS 仍 < 0.003 就弹提示
「共享屏幕时没勾『同时分享系统音频』，或对方的声音没走这个设备」，并在面板里留一行说明。

顺带：实时转写行现在带说话人归属（`我：` / `对方：`），按这句累计的左右声道能量判定，
比只看整段更稳。这个归属也直接喂给 10.8 的代答——模型得知道哪句是对方问的。

### 10.10 音色语料池：为什么「越用越像」不是靠训练

先把一件事说清楚，免得期待错位：

> **CosyVoice2 是 zero-shot 克隆，它不训练你的声音。**
> 每次合成都是拿一段 3~30 秒的参考音（`prompt.wav` + `prompt.txt`）现场提取音色。
> 所以「越用越像」的真实含义是 **参考音越干净、越覆盖你说话的常态 → 合成越像**，
> 而不是模型被你喂得越来越像。

`voice_corpus.py` 做的就是这件事：把每次录音里「确定是你」的干净片段攒起来，
再从池子里挑最合适的几段拼成新的参考音。

```
每次归档 ──→ 挑段（本人 + 够长 + 够响 + 没助理声音 + 声纹复核通过）
                ↓
        data/tenants/<owner>/voice_corpus/<场景>/<片段>.wav
                ↓
          build：**单段优先**——挑一段 4.5~9 秒连贯的话，不剪不拼
                ↓
        ~/tts/voices/<人名>/<场景>/prompt.wav（旧的自动备份成 prompt.bak-*.wav）
```

用法：

```bash
python voice_corpus.py collect                      # 扫全部归档（可反复跑，按 sha256 去重）
python voice_corpus.py list                         # 看池子：几段、多少秒、按设备分布
python voice_corpus.py build --name 张三           # 只产出 prompt.candidate.wav，不动现用音色
python voice_corpus.py build --name 张三 --install # 替换（旧的备份保留，可回滚）
python voice_corpus.py collect --profile 开会        # 按场景分开攒
python voice_corpus.py collect --profile 方言 --only 1426   # 只收某一段归档
python voice_corpus.py add --profile 方言 --audio clip.wav --text "逐字稿"  # 长段落手动加一段
python voice_corpus.py build --concat               # 强制拼接多段（默认不这么干）
```

**参考音不是越长越好。** 2026-10-19 实测：3 段共 15.66 秒的拼接版，听起来反而不如
原来那条 3.1 秒的「喂喂，能听到吗？」像本人。原因是拼接口的停顿、语速、音量都不连续，
CosyVoice 会把这种「抖」一起学进去。所以 `build` 默认**只取一段**连贯、干净、语速正常的话；
只有池子里确实没有 ≥3 秒的段时才退回拼接。要拼得更好，先让录音本身连贯，而不是靠后期拼。

**为什么不能随便拼**：参考音的文本必须和音频**逐字对应**，CosyVoice 靠它对齐音素。
所以这里只做「整段搬运」——不裁剪、不改写 ASR 文本，宁可少攒也不拼错。
`build` 会把选中的每段文本打出来，你能看出 ASR 有没有听错（错字会让音色轻微漂移）。

**三道防污染**：

| 关卡 | 作用 |
|---|---|
| 说话人标签 | 只收 `speaker_names` 里记成本人的段 |
| 声纹复核 | 段级 embedding 与本人模板 ≥ 0.28 才收（异人实测 0.11，同人跨语域 0.30） |
| 助理时间线 | 与播报区间重叠 ≥15% 的段直接跳过，避免把克隆音当成新语料 |

**设备维度**：不同麦克风录出来是不同音色（耳机麦 / 手机外接 / 笔记本内置）。
前端在开始录音时上报 `mic`，归档写进 `meta.json`，语料按 `<设备>_<归档>_<时间>.wav` 命名。
`build --device 耳机` 可以只挑某个设备攒的片段。

**自动收集是默认开的**（`VOICE_CORPUS_AUTO=0` 可关），但**自动替换音色是关的**。
理由：重建是好操作，覆盖是坏操作——万一某次录音质量差，自动覆盖会让分身突然变声。
所以设计成「自动攒，手动换」，且每次 `--install` 都留 `prompt.bak-时间戳.wav`。

实测（2026-10-19，4 段归档）：收进 4 段共 17.5 秒，`build` 取 3 段拼成 15.66 秒，
与原来那段 3.1 秒的「喂喂，能听到吗？」并存为两个音色（`zhangsan` / `张三`）。
真机 A/B 后结论是**短的更像**，于是把拼接版移出音色列表（`~/tts/voices_rejected/`），
默认继续用 `zhangsan`；方言音色则从 `会议_1200` 里单独建（见 10.13）。

⚠️ **口音会一起被克隆**：方言参考音 + 普通话文本 = 带方言腔的普通话，不是方言朗读。
这恰好是「场景模拟」想要的效果，但别指望它用方言念字（除非文本本身就是方言写法）。

### 10.11 每次归档都有唯一 ID：一个 ID 对上一整段

页面顶部回放条下面会显示 `ID  M20260101-090000-aaaa`，点一下复制。
格式是 `M + 日期 + 时间 + 音频哈希前 4 位`，即使目录被改名也不变。

它同时写进：

| 位置 | 字段 |
|---|---|
| `meta.json` | `meeting_id`（另有 `owner` / `title` / `sha256`） |
| `transcript.md` / `report.md` | 头部 `meeting_id: ...` |
| `transcript.json` | `meeting_id` |

查法（带口令 cookie 或 `?k=`）：

```bash
curl -s "http://127.0.0.1:8848/api/meeting?id=M20260101-090000-aaaa"
curl -s "http://127.0.0.1:8848/api/meetings?limit=20"     # 最近 20 段，带 ID
```

返回里有 `audio_url`、`transcript`、`report`、`owner`、`dir` 和 `meta`。
所以「我提供 ID，你就知道是哪段」这件事是可验证的，不靠记目录名。

### 10.12 实时面板里，助理的话不再经过 ASR

以前助理的合成音经 CABLE 回到声卡，被 ASR 又听了一遍：文本有错字、标成「对方」、
还会和真人说的混在一起。现在改成两条来源：

1. **助理台词用草稿原文**，在面板上单独一行（「助理（我的声音）」）。
   已经说出去的字正常色，还没说的字压灰；被打断后剩下的部分划掉，
   并标注「说到一半被打断」。看面板就知道它说到哪、哪句没播。
2. **ASR 的助理回声直接丢掉**：定稿行如果 60% 以上落在播报区间里、且能量在右声道，
   就不进实时面板，也不进对话上下文（上下文用播报日志原文，避免模型学错字）。

最终转写稿同样按播报日志纠字：`apply_assistant_timeline` 不只是换标签，
还会把「一七度」「六和九」这类 ASR 听错的文本替换成日志里的
「11到17度」「69%」。被打断的句子只保留 `spoken_chars` 那一段。

顺带把首句延迟压了一截：

| 项 | 之前 | 现在 |
|---|---|---|
| 单句切分上限 | 60 字 | 30 字（首句合成更快出声） |
| 模型 max_tokens | 220 | 160 |
| 面板反馈 | 等草稿回来才动 | 立刻显示「正在想…」，草稿到了换原文 |
| 延迟观测 | 看不到 | 显示「想了 1.2s」+「首句合成 2.4s」 |

延迟的构成（2026-10-19 实测）：静音断句 ~0.9s + LLM ~1.5~2.5s + 首句 TTS ~1.7~2.4s
+ 音频链路 ~0.3s。TTS 冷启动是最大头，所以句子越短、首句越快。

### 10.13 方言场景：音色 + 用词分开管

同一个人「开会的声音」和「老家的话」是两套模板：

```bash
# 声纹：用那段 54 秒的方言录音入库，场景记成「方言」
python tools/speaker_cli.py enroll --name 张三 --audio <会议_1200.wav> --profile 方言

# 音色：这段录音是 3 个长段（26/15/13 秒），过不了语料池 2~9 秒的筛子，
# 所以用 voice_register 截一段 8.6 秒、自动转写做逐字稿，再手动加进池子
python voice_register.py --name 张三 --profile 方言 --audio <会议_1200.wav> \
    --start 39.28 --end 47.90
python voice_corpus.py add --profile 方言 --audio ~/tts/voices/张三/方言/prompt.wav \
    --text "$(cat ~/tts/voices/张三/方言/prompt.txt)"
python voice_corpus.py build --profile 方言 --name 张三 --install
```

页面的音色下拉会多出一个方言音色项。合成时按场景选：
普通话用普通话音色，跟家里人说话用方言音色。

用词方面，把 `DIALECT.example.md` 复制成 `DIALECT.md`（已在 `.gitignore`，
不入库）再按自己家乡补词表。这些词只是参考，不强制替换：
数字、时间、金额、专有名词一律保持普通话读法；拿不准的词保留普通话，不硬造。

`.env` 里的 `ASSISTANT_HOMETOWN` 可以把家乡传给模型，作为「对方说方言时怎么接」的提示。
**留空则方言提示段整段不出现**，模型一律按普通话回答 —— 这是可选增强，不是必配项。
填到市/县即可：这个值会随每条请求发给大模型，不要写精确住址。

⚠️ 方言词汇表需要本人校对。觉得「不像」的词直接删——这张表要越用越准，不是越长越好。

### 10.14 用颜色区分说话人（实时面板 + 转写稿）

同一套配色贯穿实时面板、认领卡片和转写稿，翻稿子时眼睛能顺着颜色走：

| 角色 | 颜色 | 规则 |
|---|---|---|
| 助理 | 固定紫（`--spk-asst`） | 不参与哈希，永远同一个颜色，带 `AI` 角标 |
| 其他人 | 8 色轮转（`--spk1`~`--spk8`） | 按名字哈希取号，**同一名字永远同色**；同屏撞色才顺延一格 |

实现要点：
- 颜色写在 CSS 变量里，浅色/深色主题各一套，不靠 JS 拼十六进制。
- 取号是 `spkHash(名字) % 8`，不是每次刷新随机——否则同一个人在两次录音里换色。
- 实时面板：`.line .who` 直接带 `spk-N` 类；助理行另外有「已说（助理色）/ 未说（压灰）」。
- 转写稿：`transcript.md` 保持纯 Markdown（下载下来在任何工具里都能读），
  页面渲染完再做一层染色——把 `**[00:00:01] 名字**` 换成带 `spk-N` 的 `strong`。
- 下载的 `.md` 不带颜色，这是故意的：颜色属于界面，文档要能随便转存。

### 10.15 电脑默认音色：让对面一听就知道是 AI

克隆音色像你本人，适合「替你说话」；但有些场合需要对方**立刻意识到这是机器**。
音色下拉因此分两组：

```
我的声纹（像你本人）
    音色：zhangsan
    音色：张三 · 方言
电脑声音（一听就是 AI）
    电脑 · 晓晓（女声 · 自然）
    电脑 · 云希（男声 · 年轻）
    电脑 · 云健（男声 · 沉稳）
    电脑 · 晓伊（女声 · 活泼）
    电脑 · 晓北（女声 · 东北话）
```

实现：电脑音色统一用 `sys:` 前缀，走 Edge 神经语音 → ffmpeg 解成 24k 单声道，
和克隆音色共用 `/tts`、缓存和流式接口。选择记在浏览器 `localStorage`，刷新不丢。

```bash
# 依赖（装在合成用的独立环境里，不进转写环境）
~/tts/venv/bin/pip install edge-tts
```

实测（2026-10-19）：5.1 秒的句子合成耗时 1.7~2.4 秒，比 CosyVoice 首句还快；
命中缓存后接近 0。**需要服务器能出外网**，不通会明确报错，
不会偷偷回退成你的声音——那会把「这是 AI」这个提醒直接抹掉。

标签也跟着音色变：`sys:*` → 「助理（电脑声音）」，克隆音色 → 「助理（我的声音）」，
写进实时面板、会话上下文和最终转写稿（`assistant_label()` 按事件里的 `label` 取众数）。

### 10.16 没人说话时冒出来的「的的的的」：噪声幻听闸门

**现象**（一次真实会话）：实时面板上不断出现没人说过的话——
「就是我个的的的的」「我的的的的的的」「亲我现在」；助理还据此回了一句
「听着有点乱，你再说一遍要问啥？」。而最终转写稿是干净的。

**原因不在麦克风"坏了"，在流式模型的行为**：paraformer 流式在**没有语音**时也会继续解码，
底噪、按键、截图音效都能被"续写"成字。实测那段录音的麦克风声道能量：

| 场景 | RMS |
|---|---|
| 底噪（静音段） | 0.0007 ~ 0.0018 |
| 真人说话 | 0.02 ~ 0.11 |

也就是说，噪声行和真话在能量上差 10 倍以上，判起来毫不含糊。

**两道闸门**（`server.py::looks_like_noise` + `LiveSession.rms_floor`）：

1. **能量**：本句峰值 < 闸门就整句丢弃。闸门 = `max(0.0035, 最近能量中位数 × 4)`——
   用中位数而不是固定值，是为了适配不同麦克风的增益（中位数≈"没人说话时"的电平）。
2. **形态**：单字刷屏（「的的的的」占 45% 以上）、连续同字占 40% 以上、两字全重复（「我我」）。
   只看形态，不猜语义，所以宁可漏也不误杀：「哈哈哈」「好」「我」都算正常说话。

丢弃发生在**三个地方**，一个都不能少：

- `partial`：还没定稿的字幕也不推给面板（`quiet: true`，前端清掉占位行）；
- `line`：定稿行不进 `session.lines`、不推面板，并发 `{"type":"drop"}`；
- 助理上下文：`/api/assistant/reply` 前再过滤一遍——这是「助理答非所问」的根源。

日志会留证据，方便复盘：

```
丢弃噪声行 02:20→02:24 峰值 0.0016（闸门 0.0035）「我的的的的的的」
```

**代价**：极轻的耳语（< 0.0035）在实时面板里不显示。最终稿不受影响——它是停止后
用离线管线重新转写的，阈值和实时完全不同。

### 10.17 「回答要等很久」拆开看：三段各自能压多少

等待不是一个数，是四段相加。2026-10-19 实测（同一句话：明天天气怎么样）：

| 环节 | 之前 | 现在 | 怎么改的 |
|---|---|---|---|
| 说完 → 定稿 | 0.9s 静音 + 最多 0.6s 块 | 0.75s + 最多 0.6s | `SILENCE_FINALIZE_SEC` 0.9→0.75 |
| 代答（DeepSeek flash） | 1.5~3.5s | 1.6~1.85s | 首次查天气 3.4s → 开场预热缓存（`_warm_weather`） |
| **首句合成** | **3~5s** | **1.0~1.2s** | 首句按标点再切一刀（4~10 字） |
| 合计 | 7~11s | **约 4s** | — |

关键在第三行：CosyVoice2 的 RTF≈0.45，**合成 30 字要 5 秒**，而人耳在等待时是按
"第一声什么时候出"算的。所以 `splitScript` 把首句切到 4~10 字（"明天杭州阴，"），
后面的句子靠**预取 3 句**顶着——合成比播放快一倍，只要提前排进队列就不会在换句处卡住。

```bash
# 量一遍自己的链路（推 6 秒真实语音 → 代答 → 首句合成）
.venv/bin/python tests/measure_latency.py
```

再快就得动**流式合成**（`/tts/stream` 已经能出裸 PCM16，页面还没接）。
现在的瓶颈是 LLM 那 1.7 秒，TTS 已经从 5 秒降到 1 秒，收益边际递减。

### 10.18 谁能把助理叫起来：四档，默认只听我的

旧版只判文本不判人：`maybeWake(text, who)` 的 `who` 传进来却没用上，结果是
**对方说一句「你们公司有助理吗」也会触发代答**，而我把麦关了想让助理顶着时它反而不出声。
现在按「谁在说 × 什么档位」判：

| 档位 | 谁能唤起 | 窗口内续聊 | 典型场景 |
|---|---|---|---|
| `strict`（默认） | **只有我**喊唤醒词 | 也只认我说的 | 一般会议；防止对方的话被当指令 |
| `guest` | 我或对方，喊了都认 | 双方都算 | 已告知对方有这个助理，允许它帮腔 |
| `open` | 谁说话都接 | 不分谁 | 演示 / 单人自述 |
| `proxy` | 我闭麦时，对方说话**自动代班** | 同左 | 关麦让它替我谈，我打字或看提词 |

判定收在一个纯函数里（`web/app.js` 的 `wakeDecision`），单测直接把它从源文件抽出来跑：

```bash
node tests/wake_decision_test.js     # 16 项，含反向对照
```

两个实现细节值得记一笔：

- **说话人标签由后端下发**：`ready` 消息里带 `self_name` / `peer_name`，前端不硬编码「我 / 对方」。
  否则一改 `DUAL_SELF_NAME`，判定就整体错位。
- **单声道时 `who` 为空**：分不清是谁，按「可能是我」放行。这是有意的降级——
  不这么做的话，不用双路分轨的人永远唤不醒助理。

### 10.19 只听不说、收藏、音频留存

三件互相配套的事，解决「共享空间里不想让旁人听见 AI 出声」和「录音越攒越多」：

**① 出声开关**（与「语音助理」并列，是两个开关）

| 开关 | 关掉之后 |
|---|---|
| 语音助理 | 完全不响应，等于下线 |
| **🔊 出声** | **照样听、照样想、照样把文字给到面板，只是不合成不出声** |

自动接话受它管；手动按「让它说」「接一句」不受影响——手动是明确动作，不该被常驻开关按住。
这条路径就是后面提词器要接的地方。

**② 收藏**（结果面板右上角 ☆）

收藏只干一件事：**让这场录音的原始音频免于定期清理**。转写稿和纪要本来就不清，
所以星标不是「保存稿子」，是「保住录音」。标记落在 `<归档目录>/.favorite`，
不用 `meta.json` 字段——那个文件会被重建流程整份覆写。

**③ 音频留存**（`deploy/retention.py` + `meeting-retention.timer`，每天 04:30）

```
音频 > 60 天  →  mv 到 ~/data/trash/<owner>/<日期>/<归档名>/  →  再留 7 天  →  真删
文本（md/json） →  永久保留（体积极小，删了不可再生）
有 .favorite   →  整个目录跳过
```

清理**不直接 rm**，中间隔一层回收站，给「删错了」留反悔窗口。日期按目录名里的会议日期算
（换机器拷文件不会改变它），目录名没有日期才退回用 mtime。

```bash
python3 deploy/retention.py                    # 预演，只报告
python3 deploy/retention.py --apply            # 真执行
python3 deploy/retention.py --days 0           # 反向对照：确认规则真的会命中
```
